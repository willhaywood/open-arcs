# Arcs Digital — UI

Status: implemented in `apps/web`. A working hotseat client, verified in-browser playing a
real game (lead → declare → pips → Move/Battle, follow, turn advance).
Date: 2026-07-23

## 1. Shape

A Vite + React SPA. One screen: a board, a status column, an action panel, a log. It is a
**hotseat** client — the human drives whichever faction the engine is currently asking. This
matches the engine exactly: the UI holds no rules knowledge and renders whatever
`Ask(faction, actions)` it is handed (docs/02 section 6).

```
apps/web/
  index.html
  vite.config.ts        server.fs.allow ['../..'] so the engine's TS source resolves
  public/game-assets -> ../../assets/images   (symlink; real art, gitignored)
  src/
    store.ts            the engine IS the store; one useSyncExternalStore
    App.tsx             layout + new-game gate + undo/save/load toolbar
    theme.ts            faction colors
    components/
      NewGame.tsx       players (3/4), board, seed
      Board.tsx         schematic SVG board
      Hand.tsx          the current player's hand, fanned along the bottom
      PlayedCards.tsx   each faction's played tableau, down the left
      CardFace.tsx      one card: real art with a drawn fallback
      PlayerBoards.tsx  the player boards along the bottom, all four factions
      ActionPanel.tsx   renders non-card actions as buttons; game-over screen
      LogPanel.tsx      the engine log, auto-scrolled
```

## 2aa. The start screen

The header art (`assets/images/arcsheader.jpg`, served through the `game-assets` symlink) runs
full-bleed across the top and fades into the panel, and the screen is black/grey/gold like the
board's own furniture — the blue UI accent belongs to in-play affordances, not the title screen.

**Setups are dealt as cards, not chosen from a dropdown.** The board used to be a `<select>` of
engine identifiers (`Board3CoreConflict`), the one place the game's own vocabulary was thrown
away: the physical game hands you a deck of setup cards. So they are dealt the way cards are:

1. **shuffled face down** (Fisher-Yates; the deck order is cosmetic, so it does not come from the
   game seed);
2. **you take one** — it lifts and takes a gold edge, but stays face down;
3. **Start turns it over**, and the screen holds there showing what you drew, the rest of the deck
   receding;
4. **Continue** enters the game.

The names are deliberately not rendered until the reveal. Printing them under face-down cards
would make the shuffle decorative, since you would simply read the one you wanted. The name row
keeps its height while blank so turning a card over does not shift the row. Drawing blind should
not be able to trap you, so the reveal also offers *Shuffle and deal again*.

**Nothing is selected initially, and Start stays disabled until something is.** This is not
ceremony — `board(name)` is a required parameter the engine never defaults, and HRF validates the
same thing explicitly, refusing to start with `"Select a Setup Card"` when none is chosen
(`meta.scala` `validateFactionSeatingOptions`). Changing the player count deals a fresh deck.

Cards are listed from `boardsFor(players)` and looked up in a name → art table, so a board added
to the topology appears on its own (unillustrated, but choosable) rather than silently missing.

> **All four printed setups are offered at both 3 and 4 players.** Three of those boards —
> 3p Homelands, 4p Frontiers, 4p Mix Up 3 — have no HRF topology and were ported from the TTS
> mod; see docs/05 for the sources and the one place the two references disagree.
>
> **The 2-player deck still has art but no board.** `setup-2p-01..04` are on disk and are
> deliberately not offered, since a card that cannot start a game is worse than an absent one.
> HRF's `SetupCardOption.count = $(3, 4)` excludes 2-player entirely, so that one needs more than
> a topology entry.

## 2ab. Visual language

Black card stock, grey, and gold — the palette the printed components use. The blue `--accent`
is reserved for in-play affordances (what you can click right now); it never appears as
decoration, which is what lets a blue ring read as "this is live".

**The header carries it too.** Wordmark, board name, act/chapter/round and the toolbar buttons
are all on the display face in letterspaced caps, on near-black under a gold hairline — it reads
as printed titling rather than an application chrome bar. The buttons take the hand-cut corner
radius and go gold on hover. (The double rule was tried here and dropped: it is the panels'
device for *enclosing* something, and run flat across the top of the app it read as the same
trick used twice.)

The board is named the way players name it — **"Mix Up 1"**, not `Board4MixUp1`. The engine names
boards by identity because saves and topology lookups need that; the `Board3`/`Board4` prefix is
noise on screen, and the player count is obvious from the table. `setupLabel` in `setups.ts` is
shared with the start screen so the two cannot drift on what a board is called, and it falls back
to the raw id for any board added without a card entry.

**Type.** `--font-display` is **FM Bolyar Pro**, the game's own titling face — HRF sets
`50px FMBolyarPro-900` for the Arcs title (`arcs/ui.scala:415`), so this is the real thing rather
than a lookalike. Licensed to the project owner and self-hosted from `apps/web/public/fonts`, so
nothing depends on the network.

The foundry's stylesheet ships each weight as a *separate family* (`FMBolyar Pro 700`), all
declared `font-weight: normal` — which means `font-weight` cannot select between them and every
heading would have to name its own family. They are re-declared as **one family with real
weights**, so ordinary `font-weight: 700` picks the 700 cut. The cuts run 100/300/500/700/900,
with no 400: anything asking for 400 resolves *down* to the 300 light, which is why the wordmark
sets 900 explicitly.

It is a *display* face only — headings, labels, and figures. Body copy stays in the system sans,
which is far more readable at the sizes the log and card text run at.

> The font is commercial. Self-hosting it for the owner's own build is what the licence is for,
> but publishing the binaries in a public repository is a different act — worth checking the
> licence terms before this goes anywhere public, or keeping `public/fonts` out of the tree.

**The play area sits on the cover art** (`arcs-bg`), behind the map, the rails and the hand. Its
composition suits the job exactly: the crews and ships crowd the edges while the middle is dark
and near-empty, so the map lands on open space and the detail reads around it. A scrim over the
image holds contrast, and the map's SVG background was changed from black to **transparent** —
the viewBox is fitted with `meet`, so the map art never fills its box on both axes, and that
leftover band used to be the largest dead area on screen.

Chrome that sits straight on the art with no panel behind it (the court header, the play-rail
slot labels) carries its own text shadow, since the art is mid-tone in places and the crop shifts
with the viewport. The map's own SVG labels already stroke themselves.

**The board is a plate on top of it.** Against illustration the map stopped reading as the thing
you play on and became one more layer of picture, so it now asserts itself: fully opaque (it was
95%), a drop shadow lifting it off the art, and a frame at its edge.

The frame is borrowed from the printed **ambition track**: a heavy gold bracket at each corner
which then *opens into two parallel rails* running the length of each edge — an edge reads
`L=====`. Read off the component art: the thick bar does not thin to a single line, it splits.
The rails sit on the bracket's own two edges (±half its stroke), which is what makes them look
like the bar continuing rather than a second border floating nearby. A uniform hairline read as
a web border on artwork that has no uniform hairlines anywhere.

**Secured court cards show on the player boards** as a row of thumbnails, rivals' included
(`Secured` in `PlayerBoards.tsx`). Nothing on screen used to say who held what, so the only way
to know was to remember — and these are live abilities on top of being score: a held guild card can
add a Prelude option, unlock an alternative action, block a raid outright (Sworn Guardians) or
change what may be declared (Secret Order), and it can be stolen from a rival. A count would not
have done; *which* cards is the whole question. (Its suit icon also scores as one resource toward
Tycoon, Keeper or Empath — see `metric` — so the thumbnails carry both halves at once.) Rivals show theirs the same way because that is
public information and you cannot plan against a card you cannot see.

They are listed **by name**, not as pictures of the cards. A thumbnail small enough to fit here
was too small to identify — the art is 744x1039 and its name band ends up a few pixels tall — so
it carried no more information than a count did. The name identifies the card, and the two figures
read at a glance ride alongside it: the **suit**, because a guild's Prelude ability keys off its
resource, and the **key cost**, because that is what a raider pays to take the card off you in
battle. Both come straight from the card model (`suit`, `keys`), so they cannot drift from the
rules. The card's own text still needs the readable copy, which is a click away (`CardZoom`,
shared with the court rail so there are not two near-identical modals).

> `CardZoom` **portals to `body`**. Opened from a player board it would otherwise render inside
> `.player-boards`, which is its own stacking context at `z-index: 50` — a `position: fixed`
> child cannot escape that, so the card painted *under* the header. An ancestor `transform` would
> break it the same way, by becoming the containing block for fixed positioning. A modal covers
> the app, so it has to be a child of the app.

**The enlarged court card is the quietest frame in the app**: near-black stock, a gold hairline,
brackets barely there, and the display face on the name and labels. Everything in that view is
the card art at full size, so a frame that asked to be looked at would compete with the one thing
the view exists to show.

Its agents are drawn as **agent tokens and nothing else** — three figures rather than "red 3".
The token carries its faction's colour, so naming the faction beside it said the same thing
twice, and the count is redundant once the figures are there to be counted; it is the reasoning
behind fleets on the map applied to the court. One row per faction keeps the grouping, and the
row's tooltip still names it.

**The rail keeps a count, but not a bare one.** A card there is far too narrow to draw a figure
per agent, so its pips pair the agent token with the number on a dark chip — the same piece and
colour as the modal, saying *what* is being counted instead of leaving a naked numeral on the
card art. The leader is ringed in gold, since only a strict majority may secure.

**The player boards take the corners only** (`.pboard`, `BoardFrame`): small dimmed brackets on
a single gold hairline. The double rail belongs to the map, which is one object you look at —
four boards repeating along the bottom at that weight competed with the thing they sit under, so
the brackets carry the idiom and the edge stays quiet. The header made the same move.

Four corners need four boxes and an element has only two pseudo-elements, so a `.pb-frame` child
carries the other pair.

Both the shadow and the frame are applied to the **map art**, not to the SVG element. They cannot
be CSS on the container: the viewBox is fitted with `meet`, so the box is always taller or wider
than the painted map — measured at one size, a 616×433 map inside a 616×528 box — and a border on
the element would frame 95px of empty space. The shadow is a `drop-shadow` filter on the image;
the frame is drawn in map units at the viewBox bounds, so it lands on the art and scales with it.

> Supplied as a 2.8 MB PNG; the app loads a **0.27 MB WebP** converted from it, in line with the
> rest of the asset set. The PNG is still in `assets/images`, which is the *served* directory —
> worth deleting once you are happy with the conversion, since nothing references it.

**Edges are cut, not rounded.** Plates and tags use uneven corner radii on both axes
(`border-radius: 8px 3px 7px 2px / 3px 7px 2px 8px`) so an edge reads as hand-cut. The printed
game has torn edges everywhere; a uniform radius is the one thing that never appears on it, and
a pill is the shape that most says "web UI" rather than "table". The two large panels — the map
and the player boards — go further and take the bracket-and-rail frame described above.

### The player boards

Faction colour used to be the panel border, which put four saturated frames along the bottom of
a black-and-gold screen. The border is gold on every board now and the colour lives in the
nameplate — the same move the components make, where the board is neutral and only the pieces
are coloured. The name sits on a cut plate carrying the faction's **own ship token**, with the
lettering in that faction's colour lifted toward white (`color-mix`), because blue at full
saturation is barely legible on near-black.

**Supply counts.** Ships and agents left in the supply are shown as the pieces plus a figure.
This is not decoration — you cannot build a ship you do not have, and the board previously showed
only what was *placed*, never what was left to place. An exhausted supply turns its figure red.
Cities need no entry: they already show as the tokens covering the resource slots.

The initiative marker carries no caption — it is the game's own component and says what it is. A
*seize* keeps its word, because a tint alone cannot distinguish "holds it" from "takes it next
round", and those are different claims.

## 2a. The hand

Card plays do not live in the side panel — the current player's hand is a **fan along the
bottom of the board**, using the real component art (`CardFace` loads
`/game-assets/action/<suit>-<n>.webp`, falling back to a drawn card if the art is absent).

- **Sorted** by suit then strength (`SUITS` order), automatically.
- **Hover** raises a card to full, readable size.
- **Play from the fan**: a card with a single legal play (a lead, or a pivot) plays on
  click; a card with several (a same-suit follow can Surpass *or* Copy) shows a button per
  option on the raised card. The mapping comes straight from the current `Ask` — each play
  action carries the `card` id, so the hand just groups the offered actions by card.
- **Greyed when not playable** (e.g. during the pip phase) — shown for context, not
  interactive.

The `ActionPanel` filters out the card-play action types, so during a lead or follow it
shows only the non-card options (Pass) and points the player to the hand.

Verified in-browser: leading by clicking a raised card, a same-suit follow card offering
both Surpass and Copy, the fan re-sorting after a play, and greying during the pip phase.

### Keeping hover alive while the card moves

A raise-on-hover control that *moves the thing you are hovering* will fight the pointer
unless the hit area is built for it. Two defects made the Surpass/Pivot buttons unclickable,
and both are worth not repeating:

1. **The lift stepped out from under the pointer.** At rest a card's bottom sits on the row's
   bottom edge; hovering translates it up 120px and scales it 1.5. A pointer anywhere in the
   card's lower half then finds itself *below* the raised card — hover drops, the card falls
   back under the pointer, and it oscillates. `.hand-card::after` extends the hit area
   downward past the resting position (the parent's scale applies to the pseudo-element too,
   so 104px of strip covers 156px of travel), with a 14px lateral overhang because the fan's
   outer cards un-rotate as they rise and pull their edges inward.
2. **A dead band between card and buttons.** The button row was offset with `top: -34px`,
   leaving a gap belonging to neither element; crossing it dropped hover. It is now anchored
   with `bottom: 100%` and the gap expressed as `padding-bottom`, so the two boxes touch.

Verified by hit-testing rather than by eye: force the hover styles, wait out the 0.16s
transition, then check `elementFromPoint` for every point that owns the hover at rest and
along the path to each button. **0 losses across 10,104 sampled points on all six cards, and
0 breaks on every card-to-button path.** Sampling before the transition settles measures the
resting layout and proves nothing — the earlier pass looked clean for exactly that reason.

## 2. The store is the engine

`store.ts` holds a single `RuleResult` and exposes `start(options)` and `apply(action)`:
`apply` is just `advance(state, action, registry)`. `useGame()` is one
`useSyncExternalStore`. There is no second source of truth, no reducer, no game state in
React — the engine owns it, React renders it. This is the payoff of the pure-engine design:
the entire UI-to-rules binding is ~40 lines.

## 2b. The round play area (left of the board)

`PlayedCards.tsx` reproduces the physical board's left-hand card slots: a tall
**SURPASS, COPY OR PIVOT** frame above a single **LEAD** frame, gold-bordered with the label
running vertically up the frame edge, as printed on the board.

It is fed by `state.roundPlays`, so — like the physical board — it shows **the current round
only** and clears when the next round begins. Each card is bordered in the playing faction's
color and tagged with how it was played. **Copied cards are shown face down** (`card-back`),
as they are played at the table.

**Cards lie flat**, rotated 90° counter-clockwise, so they sit on the board rather than
standing up. The slot footprint is landscape (`--card-w`/`--card-h` on `.play-rail`) while
the card image stays portrait and is turned into place — sized `h x w` then rotated, so the
744:1039 ratio stays true.

**Follows land bottom-to-top.** The rail is the physical board's row of card slots turned 90°
counter-clockwise, so the left-to-right order cards are laid down in at the table reads
bottom-to-top here: the first follow sits at the foot of the frame, directly above the LEAD
card, and later ones stack upward.

Two things are needed, not one. `flex-direction: column-reverse` reverses the order, but the
group must also be pinned to the bottom of the frame — and `.play-slot` is
`align-items: flex-start`, so `.slot-cards` is only as tall as its cards. Without
`align-self: stretch` the reversal just flips the cards *at the top of the box*, which is not
what the eye reads as landing bottom-to-top. Only the tall slot is reversed; the LEAD frame
holds one card, where order is meaningless and the change would only move it off its top edge.

**The "Ambition Declared" token** is drawn in CSS to match the physical piece: a black pill
with a white **0** ring at one end and the words in white caps. It is laid on the card of a
player who declared an ambition, **with the 0 covering the card's printed number** — which is
the whole point of the piece, since a declared card counts as strength 0.

Placement works because the card image and anything sitting on it share one rotated frame
(`.slot-card-rot`), so overlays are positioned in the card's **own portrait coordinates** and
turn with it. The number is at roughly 7–24% across and 4–14% down (measured from the card
art); the token's 0 lands on it at 7.5–22.5% × 3.1–13.8%.

The pill spans ~92% of the card width. Its gutters are set with `left` **and** `right` rather
than a `width`, which is what guarantees they stay equal on both sides at any card size.

It is driven by the engine's existing `lead.zeroed` flag, so the marker on screen and the
surpass rule cannot disagree. (`action/zeroed.webp` exists in the assets as a plain 0 token,
but the drawn pill matches the real component more closely.)

`roundPlays` is a small engine addition made for this: `{ faction, cardId, kind }` appended
by the lead/surpass/copy/pivot handlers and cleared at round start, on a pass-driven round
change, and at chapter start. The previous version of this component showed a per-faction
tableau of the whole chapter's played piles, which did not match the board.

## 2bb. The player boards (bottom strip)

`PlayerBoards.tsx` puts the physical player board along the bottom: a **full board for
whoever is acting**, and a **compact one per rival** to its right. The physical board's
printed prose is dropped; its functional parts are kept.

**Six resource slots**, each under its printed key banner (`icon/keys-N.webp`). A filled slot
shows the token art, an open one an empty well, and a slot past capacity is hatched out.
Both the key costs and the capacity come from the engine's own `CITY_SLOT_KEYS` (`[3, 1, 1,
2, 1, 3]` — these match the physical board exactly) and `slotCapacity(citiesInReserve(...))`,
so the board cannot drift from what a raid or a score actually does. Building cities opens
slots, which the UI shows without any extra bookkeeping.

**The +2 / +3 "to won ambitions" shields** light up off the same city count the scorer uses
(`citiesInReserve < 2` and `< 1` in `ambitions.ts`), so they are a real readout, not decoration.

**Trophies** and **captives** are counts of `Location.trophies` / `Location.captives`.

**The initiative marker** is the real component art (`icon/initiative.webp`), standing hard
against the **left edge** of the board it belongs to — the way the physical piece sits beside
a player's board. `.pboard` is therefore a row of `[marker | .pb-body]`, where the body is the
old vertical stack. No plate and no divider: it should read as a token resting against the
board, not as another panel.

- **Plain token, gold glow — "Initiative"**: holds it now and leads this round.
- **Dimmed, warm glow — "Seized"**: has claimed it for the *next* round.

Both can show at once, and that is the honest rendering: a seize does **not** move the marker
when it happens. It is a claim that settles at end of round (`nextInitiative` in
`rules/turn.ts`), so one faction is leading now while another is taking it next. Mini boards
show the token alone; there is no room for the word.

The art is a clean cut-out on a transparent background, and at 400x1100 the piece fills the
frame — so the element is sized straight to the artwork with no gutter to absorb. An earlier
1024x1536 version carried wide margins, which forced a larger box to reach the same visible
token.

**Locked slots show the city that covers them.** This is the physical board's central idea and
the UI originally hid it behind a grey hatch: your unbuilt cities *sit on* the later slots.
Building one takes it off the board and reveals what was underneath. Each locked slot now
draws your faction's city art with the ordinal of the city that opens it, and the inactive
+2 / +3 shields do the same:

| Opens after | Slot |
| --- | --- |
| 0 cities | slots 1-2 |
| 1st city | slot 3 |
| 2nd city | slot 4 |
| 3rd city | slots 5 **and** 6 |
| 4th city | +2 shield |
| 5th city | +3 shield |

Consecutive slots opened by the *same* city are grouped, and the token is drawn **once across
the group** — the 3rd city sits over slots 5 and 6 as a single piece rather than being stamped
on each. **Being one token rather than two is what carries the meaning**, so it stays the same
size as every other city and simply covers a two-slot group partially.

The sizes have to be pinned to make that hold: `object-fit: contain` scales to the box, so a
two-slot group is wider and would paint a *larger* token from the same rule. Setting the
height to the well width caps both — measured 30px on the full board and 20px on the minis,
identical whether the group is one slot or two.

The thresholds are derived from `slotCapacity` at render time rather than hardcoded, so they
cannot drift from the rule.

Verified in play: each faction places one city during setup, so a faction with two more built
(three total) shows **0** locked slots while the others show **2**.

### Outrage

Rendered the way the table does it — the token's flipped art
(`icon/<resource>-outrage.webp`, which ships for all five) plus a red ring so the blocked type
is obvious at a glance. Driven by the engine's `outragedResources(state, faction)`.

The full board shows all five types so an un-outraged board still reads as a row of tokens;
the minis show only the outraged ones, so a clean rival board stays clean.

Razing a city outrages the **attacker** — see docs/09 section 3a. The engine enforces the
discard-on-provoke immediately, so the resource slots and the outrage strip both change on
the same battle.

### Layout

A third row on `.board-col`, below the hand. It costs the map ~145px of height (the map is
height-constrained, so this is a real trade). `.player-boards` sits at `z-index: 50`, above
`.hand` at 40, so the hand cards' hover strips — which overhang the row — do not swallow the
boards' tooltips. That is safe because a strip only has to cover its own card's *resting*
area, which is inside the hand row above. Re-running the hand hit-test with the boards in
place confirmed it: still 0 hover losses and 0 broken paths to the buttons.

Cross-checked against engine state by driving a game and comparing: filled-slot counts match
`countResource` per faction, no token ever sits in a hatched slot, capacity grows as cities
are built, and the trophy tally follows the battle log.

**`StatusPanel` is gone.** It showed power, resources, trophies and captives for all four
factions, which this strip now carries in full. Its one non-redundant part, the
`Act / Chapter / Round` heading, moved to the topbar; `.swatch` is the only style it owned
that survives (the player boards and the game-over card both use it), and `RESOURCE_ABBR` /
`RESOURCE_COLOR` went with it since nothing reads them once the real token art is in use.
The right column is now just actions over a scrolling log.

### The hand sinks behind the boards

Cards rest with only their top ~93px showing. `.hand-row` is shorter than a card and `.hand`
hangs 84px past it, reaching 110px into the boards row. This is what bought the map its height
back: 601px -> 677px.

**The overhang is clipped at `.hand-row`, not hidden behind anything.** Hiding it originally
needed a solid tray spanning the whole boards row, because the boards themselves did not cover
the fan: they stopped short of it horizontally, the fan crossed the 10px gaps between them, and
their translucent panels showed the cards straight through besides. That tray is gone now that
the boards float centred, so `.hand-row` carries `clip-path: inset(-600px -600px -10px -600px)`
instead — cutting the fan exactly where the tray's top edge used to be (the row's bottom plus
the grid's 10px gap, measured as the same y as the boards' top). Only the bottom is clipped;
the generous negative insets leave the hover lift, which raises a card 120px and scales it,
completely free.

Verified the same way the tray was, by hit-testing every card point below the cut line:
**0 of 9,356 sampled points leak**. `clip-path` removes the clipped region from hit-testing as
well as from painting, so this checks both at once. All six cards stay reachable (389-534
hittable points each) and clicking one still plays it.

### The web app was not being typechecked

Worth recording, because it hid a real break. The root `tsconfig.json` referenced only
`packages/engine`, so `npm run typecheck` never looked at `apps/web` — every "typecheck clean"
in this build covered the engine alone. A `CITIES_PER_FACTION` import that the engine's index
does not export passed typecheck and blanked the page at runtime.

`npm run typecheck` now runs `tsc --build --force && tsc -p apps/web --noEmit`. Confirmed by
introducing a deliberate type error in a component and watching it fail.

A second trap in the same episode: `npm run typecheck | head -3; echo $?` reports **head's**
exit status, not tsc's. Check the exit code on an unpiped run.

A third, when measuring the spanning city: `getBoundingClientRect` on an `object-fit: contain`
image returns the **element box**, not the painted image, so it reported the token covering
both wells fully when it was letterboxed inside. Compute the painted rect from
`naturalWidth/naturalHeight` before measuring overlap — the same class of mistake as
`offsetTop` ignoring CSS transforms.

### Moving by clicking the map

Movement was the worst thing in the UI: one text option per origin-destination pair, so a
Move opened a list of a dozen lines like `Move 5-Gate → 5-Crescent (2 ships)`. Reading a
board off a list, with the board sitting right there, is the wrong shape.

The map is now the input surface. The key idea is that **the board is an alternative renderer
for the current `Ask`**, not a second input path: `moveGraph` reads the very actions the side
panel is showing and clicking a system dispatches one of them. Nothing new is invented, so
undo, save and replay are untouched — and the panel still works for anyone who prefers it.

- Systems you can move **from** carry a thin ring; the chosen one goes dashed and brighter.
- Its **destinations** carry a heavy filled ring, with dashed arrows from the origin.
- A **catapult** continuation highlights the same way, and re-highlights after each leg, so
  running the gate ring is just repeated clicking.
- A hint bar under the map says which half of the choice you are in.

**Rings are centred on the pieces, not the hub.** `render.anchor` is the hand-picked hub
point; tokens are laid out at `render.placements`, which fan up to ~100px away from it, so an
anchor-centred ring sat *beside* the fleet. `footprint()` takes the centroid of the placements
actually in use and sizes the radius to cover them.

**One colour, not two.** The first cut used blue for origins and gold for destinations, which
put two unrelated systems of meaning on a map that already spends gold on its frames and four
hues on faction pieces. Everything selectable is now the UI accent, with *state* carried by
weight and fill — thin ring available, dashed ring selected, heavy filled ring reachable.

**"How many carry on?" is drawn in ships, not words.** Beside the destination, one row per
size — four ships, then three, then two, then one — and you click the row you want to keep
moving with. The rest stay put. It applies to the opening leg and to *every* catapult leg, so
running the gate ring means picking a shorter row each jump and shedding a ship at each stop.

The rows make the trade-off visible in a way a count never does: the gap between the row you
pick and the row above it **is** the detachment you are leaving behind. Rows use the acting
faction's own ship art, and the un-hovered rows dim so the row under the cursor reads as the
choice.

The panel keeps the same options as text, so both surfaces work.

**Chrome drawn inside the SVG must be sized in screen pixels.** The board is a 2528-wide
viewBox squeezed into ~800px, so map units land at about a third of their nominal size — the
first cut used map units and produced 31px ships in 17px rows, unreadable and barely
clickable. The picker now measures the rendered SVG with a `ResizeObserver` and converts CSS
pixels to map units, so it holds a fixed on-screen size at any board scale.

That conversion has to use **both** axes: `preserveAspectRatio` defaults to `meet`, so the
smaller of the two scales wins and the other axis is letterboxed. Measuring width alone
under-reports units-per-pixel whenever the box is height-limited — at 900px wide the map is
527x307, height-limited, and the icons came out 38px instead of 46. The scale is now
`max(vbW/width, vbH/height)`, giving 46px at every width tested.

The count sits in its own reserved column. Computing the panel width from the ship rows alone
put the widest row's numeral outside the panel.

### Battling on the map

Declaring a battle uses the same idea as movement — the board renders whatever `Ask` the engine
is offering. Everything after that happens in **one battle window** (`Battle.tsx`), which keeps
the same frame and the same fleet layout from picking dice to placing the last hit.

- **Choose a system.** `battle/system` actions become warm rings on the eligible systems
  (distinct from the blue move rings); clicking one attacks there.
- **Choose a target**, when a system holds more than one enemy: coloured chips, one per colour.
  The fleets are not drawn yet — there is no single opponent to lay out.
- **Gather the dice.** The engine offers every legal split as its own `battle/roll` action; the
  window is a friendlier face over that set — one card per die type with a stepper, capped by
  the ships in the system and by which dice are legal at all (the Raid card simply does not
  appear when the enemy has no buildings to raid). Confirming dispatches the matching action.

  This started as a separate tray floating over the board, which meant the thing you were
  deciding about — the two fleets in the system — was only on screen for half the decision, even
  though the dice you may roll are capped by the ships you have there and Raid dice need enemy
  buildings to aim at. Both fleets are now drawn during the gather step too, in the same place
  they occupy during assignment (directly above the footer), so the window does not reshuffle
  under you as the battle moves from gathering to resolving.
- **Roll.** `state.lastRoll` records the faces the seeded RNG already produced; the tray rolls
  them as real 3D dice, then shows what is left to assign.

  **A roll tumbles once.** Undoing back into a battle remounts the tray, which replayed the whole
  reveal every time and made stepping back through a combat feel like wading. Rolls already
  watched are settled on sight. A roll is identified by *where it sits in the journal* as well as
  its faces — faces alone are far too weak, since a single skirmish die has only six outcomes and
  unrelated battles would collide constantly. It is marked watched when the motion *finishes*,
  not when it starts, because StrictMode invokes the effect twice on mount and marking it up
  front would let the second pass suppress the animation the first pass was starting. (One honest
  consequence: undoing a roll and re-rolling the *same* pool replays nothing, because the engine
  is deterministic and it is genuinely the same roll.) Each die is a CSS cube carrying its
  type's six face arts, and a single eased `transform` transition through several whole turns
  does the whole tumble-and-settle — the ease-out reads as a die decelerating to a stop, with no
  animation loop to drive. The face art is a disc on a transparent field, so it is scaled past
  the inscribed-circle ratio (√2) to fill each square face; at natural size the cube reads as
  floating blobs with dark corners. The motion is keyed on the roll's contents, so it plays once
  per battle, not once per hit — and it never decides a face.
  **The art files are not numbered by the engine's face order.** `icon/<type>-die-<n>.webp` is
  numbered by the *physical* die; `FACES` in the engine follows arcs_tts `DiceCounter.lua`. Those
  differ, so indexing the art by the rolled face number drew the wrong symbols — Assault face 1
  (2 hits + self) drew art file 1, which is blank, and players correctly noticed the dice did not
  add up to the tally. `apps/web/src/dice-art.ts` records what each art file actually shows and
  the permutation between the two (`[4, 1, 5, 2, 3, 6]`, the same for all three dice);
  `test/dice-art.test.ts` asserts the mapped art matches the rolled face symbol-for-symbol, so
  drift on either side fails a test rather than quietly lying to the player.

- **Assign the hits**, in `DamageAssign.tsx` — your force above and theirs below, every piece its
  own sprite. One click damages a fresh piece, a second destroys it, which is exactly the engine's
  health model. Hunting for pulsing rings on the map made you read the board twice: once to find
  the pieces, once to work out which were still legal targets.

  A piece is clickable exactly when the engine is offering a `battle/hit` for it. Nothing about
  legality is decided in the UI, which is what keeps the phase order (own ships → enemy ships →
  enemy buildings) and "Cities only when building hits are being placed" honest for free.

  **Destroyed pieces keep their slot.** A destroyed figure leaves the system, so a roster read
  from live state alone would drop it and the row would reflow under the cursor mid-click. The
  roster is the pieces in the system *plus* every target named by this battle's trailing
  `battle/hit` journal entries — derived rather than snapshotted, so it survives undo, remount and
  loading a save mid-assignment. Those pieces render as the colourless `*-empty` silhouette that
  the board already uses for unbuilt building slots.

  **Undo is the journal, again.** "Undo last" is one `store.undo()`; "Start over" drops the whole
  trailing run of hits and returns you to the moment after the roll. No bespoke undo stack — the
  same replay that powers the toolbar's Undo.

  > **A battle used to be a dead end.** Two things combined: the modal's backdrop is a
  > full-screen fixed layer, so it covered the toolbar and left Undo *enabled but unclickable*
  > (`elementFromPoint` on the button returned the backdrop); and the modal's own undo was
  > disabled until a hit had been placed. Immediately after a roll there was therefore no way
  > back at all. Fixed on both sides: `.topbar` sits above every overlay so the app's chrome is
  > always reachable, and the modal's undo is enabled whenever anything is undoable — with no
  > hits placed the previous entry is the roll, so it reads "Undo roll" and walks back to the
  > dice. Verified by unwinding a committed battle with the toolbar alone: confirm → assign →
  > gather → choose-system → pip menu → the action before it.

  The Self count is routinely larger than the self-damage flames showing on the dice, because an
  intercept adds one hit per *fresh defending ship* — a number that appears nowhere on the dice.
  The battle context carries that component as `intercepted` purely so the modal can say so
  ("Intercepted — 3 of those self-hits are the defender striking back") instead of leaving
  players to re-count the faces and conclude the tally is wrong.

As with movement, the side panel still lists every battle action as text, so both surfaces work
and undo/save/replay are untouched.

## 2c. The ambition track (right of the map)

`AmbitionTrack.tsx` uses the real board artwork — `ambitions.webp` (431×1224) — as a backdrop

## 3. The board

`Board.tsx` draws an SVG with `viewBox` = the real map size (2528×1776). **The map art is
the board** — the schematic node rings and adjacency lines an earlier revision drew are gone.
The adjacency data still drives play; it just no longer needs to be on screen.

**Token placement.** Pieces and empty slots sit at precomputed points *inside* each planet's
region, from `render.placements` in the board topology. The board art is deliberately
`map-no-slots` — HRF removes the printed slots and places both pieces and slot markers at
non-overlapping points within the region, found from the colour-indexed region bitmap
(`ui.scala:657-680`, each free slot modelled as a pseudo-figure `Figure(Free, Slot, …)`).

We do the same thing once, offline, in `scripts/compute_placements.py`: for each system it
lays a **compact cluster of points around the system's anchor** — the hand-picked point that
sits on the planet — keeping only points whose centre is in the right region, and enforcing a
minimum separation of one token width so tokens cannot overlap. Clearance and spacing relax
adaptively (`CLEARANCES`, `SPACINGS`) because the wedge regions vary a lot in width; every
system ends up with at least six points. The UI indexes into that list, so there is no runtime
bitmap work and layout is deterministic.

Two things that were got wrong first time, worth not repeating:

- **Spreading points across the region** (farthest-point sampling) put tokens out in the empty
  parts of a wedge instead of on the planet, and only guaranteed ~37px separation against a
  ~95px token — so they overlapped. The cluster-around-anchor approach fixes both.
- **Requiring the whole token to fit inside the region** starved the narrow wedges. Only the
  token's *centre* needs to belong to the system; a token may overhang the boundary, exactly
  as a physical token overhangs on a real board.
- `placementFor` steps outward diagonally past the end of the list rather than wrapping with
  `%`, which had put two tokens on the identical point.

Verified in-browser by measuring every rendered token's screen rect: **0 clashes across 34
tokens** (any pair closer than 72% of a token width counts as clashing).

**Piece art.** Tokens come from `figure/<colour>-<piece>[-damaged].webp`, at their native
on-map sizes — ships 194×81, cities and starports 122×122, agents 42×68 (these are already
the final sizes: the asset pipeline pre-scales them, so they are drawn 1:1 against the
2528×1776 canvas, then multiplied by `TOKEN_SCALE`). Starports use the **triangle** variant
(`starport`), matching the physical component and the city silhouette; `starport-alt` is the
six-pointed star HRF offers as `StarStarports`.

Pieces are grouped by **colour + type + damage state**, so a damaged piece draws its own art
(a darker, overlaid token) rather than needing a marker. All 32 fresh/damaged figure assets were
confirmed to resolve.

**Fleets are drawn as ships, not as a numeral.** A stack renders one real token per ship, each
offset up and to the right so the ones behind still show, with the stack centred on the placement
point. Ships are the piece whose count changes constantly and matters at a glance, and reading
"how big is that fleet" off a small badge meant reading a digit when the answer could just be the
silhouette. Because grouping already splits on damage state, damaged fleets stack the same way in
their own art.

Only ships stack: buildings come one or two to a system and sit in their own slots, and an agent
stack is a court thing rather than a map thing, so those keep the badge from two.

**Five hulls are drawn at most; past that only the number climbs.** Nothing in the rules caps a
fleet — neither the engine nor HRF limits ships per system, so one can legally hold a faction's
whole supply of 15, and ten is reachable in ordinary play. The cap is therefore a legibility
choice and not a rule, which is worth keeping straight: past five, hulls stop adding information
and start crowding their neighbours, so a twelve-ship fleet is five hulls and a "12".

**The count badge returns from three.** A pair of hulls is unambiguous at a glance, so two ships
carry no numeral; from three up the overlap costs a beat to count, so the badge states it. That
is what makes the cap safe — the exact number never depends on counting hulls.

**The stack is scattered, not ruled.** Every fleet climbing the same diagonal at the same pitch
read as a ladder. A stack now leans up to ~22° either side of that diagonal, and each hull takes
a small nudge and a few degrees of roll, so a fleet looks set down by hand and no two systems
stack alike.

**Fleets face both ways.** The ship art is drawn facing left, so every fleet on the board sailed
the same direction; about half are now mirrored. The facing is per *fleet*, not per hull — ships
in one system pointing different ways would read as a scrap rather than a formation — and comes
from a different seed than the lean, so pitch and heading do not correlate. The mirror wraps only
the hulls: flipping the whole group would reverse the count badge's numeral too.

That scatter is **deterministic** — a sine hash of the stack's position and the hull's index,
never `Math.random`. It has to be: a random scatter would make every fleet on the map twitch each
time any unrelated piece of state changed. Verified by snapshotting all twelve stacks' hull
positions and rotations, reloading the save, and confirming the render is byte-identical.

**Empty building slots.** Each planet shows one `building-empty` marker per *open* building
slot, from the engine's `freeSlots(state, system)` — so available spaces are visible, and a
marker is simply replaced by the real token when a City or Starport goes up. Buildings render
first, then open slots, then ships and agents, so a planet's building area reads together.
Verified on Board4MixUp1: 22 slots across the in-play planets minus 8 buildings placed at
setup = **14** markers, which is what renders. The real `map-no-slots.webp`
is the backdrop (served via the `public/game-assets` symlink), and hides itself gracefully
if the asset isn't present.

**Map legibility.** The map is drawn at `opacity 0.95` over a flat near-black, and the
system nodes are translucent rings rather than filled discs, so the artwork reads through
them; labels carry a text outline to stay legible. (An earlier revision had the map at 0.28
with opaque nodes over it, which made the board look very dark — the art was there, just
buried.)

**Out-of-play clusters.** Arcs uses fewer clusters at lower player counts — four at three
players, five at four — and the board art ships an overlay per cluster for exactly this.
For every cluster in 1–6 that is not in `state.board.clusters`, the component draws
`map-out-N.webp` at (0,0), full map size, as HRF does (`arcs/ui.scala:539-543`).

Each overlay is a single transparent layer carrying **both** things at once: the dark
starfield that blanks the cluster, and the **gold double-headed gate arrow** showing where
the gate ring now routes around it. So the "block it off" and "show what happens when ships
traverse" requirements are one asset, not two — no separate arrow markers are needed.

Verified: Board4MixUp1 (1,2,4,5,6) blanks cluster 3 with one arrow; Board3MixUp (2,3,5,6)
blanks clusters 1 and 4 with an arrow at each. Nodes and pieces are unaffected because
`board.systems` already excludes out-of-play clusters.

**Not used: `map-ambitions-3` / `map-ambitions-4` — a deliberate deviation, not an oversight.**

These are full-map overlays carrying the same five ambitions, hex marker slots and cleanup
notes as the side panel, re-laid-out to fit the wedge of the cluster they replace (`-4` wide
across the lower-left, `-3` compact in the lower-right). HRF draws one on top of `map-out-N`
and then places the chapter marker and goal token inside it (`ui.scala:545-568`).

This is how the **base game** shows ambitions. Every base-game layout puts exactly cluster 3
or 4 out of play — by design, so the on-map display always has a home:

| Board | Out | Hosts ambitions |
| --- | --- | --- |
| Board3MixUp | 1, 4 | cluster 4 |
| Board3Frontiers | 2, 3 | cluster 3 |
| Board3CoreConflict | 3, 6 | cluster 3 |
| Board4MixUp1 | 3 | cluster 3 |
| Board4MixUp2 | 4 | cluster 4 |
| BoardFull | none | — separate panel |

The tall `ambitions.webp` we use for the side track (section 2c) is drawn by HRF only inside
`campaign.?(...)` (`ui.scala:180`, `:1545`) — it is the **campaign** component, needed because
the campaign uses all six clusters and has no free wedge.

**Decision (2026-07-23): keep the side panel.** It stays legible at a fixed size and is easier
to read at a glance than a small corner of the board. The costs are accepted: it is the
campaign layout rather than the base-game placement, and it spends ~148px of width that would
otherwise go to the map. Switching to the on-map overlay later is a small change — draw
`map-ambitions-N` for whichever of 3/4 is out, and drop the third grid column.

The campaign's `map-broken-gate-N-{arrow,crescent,hex}` and `map-twisted-passage` overlays are
a different mechanic — broken gates during the Blighted Reach, keyed off `game.broken` /
`game.exit` — and are phase 2, not player-count blocking.

This deviates from doc 02's "Canvas 2D with real sprite art". The reasoning: for ~24
labelled, clickable, static nodes, SVG is simpler and the canvas performance argument does
not apply. A schematic board is also more legible for developing and debugging the rules
than half-placed art would be. When component art is layered in, a canvas map/piece layer
can sit under this — the anchors and hit-geometry are already the real ones. Deviation noted
rather than silently taken.

## Selecting on the map: targeting reticles

Move and battle selections used to be plain blue circles with a straight dashed chord between
them. Blue belonged to no part of this game, and a circle drawn *in* the chart reads as printed on
it. They are now an **overlay on** the board — kit the fleet paints over the chart — built from the
vocabulary of a targeting display and in the game's own colours: **gold** for movement, the faction
**red** for battle.

`Reticle` in `Board.tsx` has four states, and the difference between them is the information:

| State | What it means | How it reads |
| --- | --- | --- |
| `idle` | a system you *could* set out from | a bare, quiet ring |
| `locked` | the origin you picked | the ring solidifies and the sweep **stops** |
| `dest` | somewhere you may go | the ring sweeps and the scale ticks light |
| `battle` | a system you may attack | the same kit in red, plus a crosshair |

The sweep stopping on `locked` is the point: a settled choice should not still be searching.

**Every reticle is drawn at one fixed radius** (`RETICLE_R`), not at the system's own. `centreOf`
sizes its circle to the painted region, which runs from 86 to nearly 300 map units — reticles at
that radius came out two and three times the size of each other and the row read as an accident.
Only the art is pinned; the hit area still uses the region's radius, so a big system stays easy to
click.

**Routes are curves, not chords.** Each bows away from the midpoint, which makes them read as
trajectories and — the practical half — stops two routes between the same pair of systems lying on
top of each other. They start and end on the reticle rings rather than in the system centres, the
dashes flow toward the destination so direction is legible without reading the arrowhead, and a
dark bed under the flow keeps them over bright artwork.

Every reticle part is `pointer-events: none`; a transparent `.sys-target` circle beside it stays
the hit area, so the art can grow without shrinking the clickable region. The animations are
decoration — under `prefers-reduced-motion` they stop, and the states still read by colour and
weight.

### The battle window wears the same instrument chrome

`DamageAssign` was already red, but its details were web defaults and its standing order — the one
line telling you what the battle wants — was the coldest blue in the app. It now matches the map:
the order is gold small-caps on a square rule (the same role the hint under the map plays, so the
same treatment), readouts are small-caps with a gold hairline instead of grey pills, the shell is
squarer and lit by a thin red filament along its top edge, and the confirm stays **red** where the
resource screens' primary is gold, because this one settles a fight.

Targetable pieces follow the reticles' rest/hover discipline: at rest a red hairline, a faint fill
and **corner ticks** on two opposite corners; on hover the fill deepens, the frame brightens and
the piece lifts. A whole fleet of pulsing boxes was a wall rather than a menu — the same reason the
map's rings were thinned.

The ticks are pseudo-elements, not a gradient border. A `conic-gradient` border paints wedges
outward from the centre, which on a box this wide crossed the ship art instead of marking its
corners.

**The raid modal is the same console in gold**, since raiding is the spoils rather than the fight:
gold filament along the top edge instead of red, a gold order bar, and the shelf on the same
quiet-rest/strong-hover split as everything else.

### The die seam, and why colour could never fix it

The face art is a disc on transparency; the CSS fills the square face behind it with the die's own
body colour to close the corners. A hairline was visible where the disc met those corners, and two
rounds of re-tinting the fill — darker, then lighter — only ever moved it.

**The fill was never the problem.** Sampling the art settles both halves of it:

- the art is **perfectly flat** — every opaque pixel of `skirmish-die-4` reads `78,125,132`, so an
  exact match *is* achievable and any tint at all shows a seam;
- the face carried `box-shadow: inset 0 0 12px rgba(0,0,0,.35)`, and **an inset shadow paints above
  the background but below child content**. It darkened the bare corners and left the disc
  untouched — lighting the two halves differently, which no fill colour can reconcile.

So the fill is back to a pixel-exact match, the vignette moved to an `::after` overlay that covers
the art too, and the cube's shape now comes from per-face `brightness()` — which takes the fill and
the art together and cannot pull them apart again.

## Decisions get screens, not buttons

Three kinds of choice now have their own surface, and the action panel is for the turn's ordinary
actions only. Each new one is filtered out of `ActionPanel`'s `ELSEWHERE` list so it cannot appear
twice.

| Choice | Surface | Why not the panel |
| --- | --- | --- |
| Drafting leaders and lore | `DraftScreen` | Choosing needs the card's printed text |
| The Archivist's keep-2-of-5 | `LearnedScreen` | Same — a pair of names in a button says nothing |
| Assigning battle hits | `DamageAssign` | The engagement is spatial |
| Arranging your resource slots | `SlotBoard` | It is an *arrangement*, not a pick — so it is the board, and you drag |
| The Prelude | `PreludeScreen` | A choice between *tokens* — and a **tray**, not a modal (below) |
| Spending raid keys | `RaidModal` | A shop: goods on one side, the dice you rolled on the other |
| Battle: target, dice, hits | `Battle` / `DamageAssign` | The engagement is spatial — and the panel yields while it is up |

`SlotBoard` replaced `OverflowModal`, which asked "which resource do you end up without" as a list
of sentences. That was only ever half the rule — see docs/07 — and the half it left out is the one
that decides *where* a token sits, which is what a raider's price is read from. So the screen is
the row itself: a key plate above every slot, a well below it, and tokens you drag between them.
The arriving token sits in its own tray until it lands.

Dropping onto a full slot **swaps** the two; landing an *arriving* token on one **ejects** the
occupant to the supply, which is the old overflow discard done with your hands instead of chosen
from a list. Legal targets light up only while something is in the air, and a landing that costs
you a resource lights red rather than gold.

Dragging is pointer-based rather than HTML5 drag-and-drop, so it works under touch and the token
can follow the cursor. A press that does not move is a **lift**, left in the air for a second
click — the accessible path, and the one the tests drive. That distinction has to be made on
*button-down movement*: an earlier cut treated any pointer movement as a drag, so moving the mouse
after a click-lift armed the next click to drop the token wherever the cursor happened to be, and
quietly discarded resources.

`RaidModal` prices its goods with the same `keys-N` plates the player board stamps on a resource
slot, and shows the purse as **the raid dice that were actually rolled**, dimming a die once all

**The Prelude is a tray, not a modal**, and that distinction is the point. It sits across the
bottom of the map column and paints over the hand — the card is already played, so the fan is
spent for the turn — leaving the map, the court rail and the player boards in view. Spending here
is decided *looking at the board*: whether a Fuel is worth a Move depends on where your ships are,
and a modal hides exactly the thing you are deciding against.

It is a **sibling** of `.hand-row`, sharing its grid area rather than living inside it, because
that row clips its children to hide the fan's overhang. Everything in it is laid out along the row
rather than down the tile, since every pixel the tray takes comes off the map: it stands 159px to
the hand row's 96px, so the map loses about 63px while it is open and nothing is covered.

One tile per resource *type* — two Fuel are one choice, and the count says how many you hold — with
what each buys as chips beside it. An outraged type keeps its place, wearing its outrage art and
able to do nothing but be discarded, because the whole cost of outrage is seeing what you cannot
spend. Guild cards sit behind a divider: they spend a *card*, not a token, and each is discarded to
use, so they carry the same magnifier `RaidModal` uses.

**The rest of the game's decisions are still buttons**, including several the label cannot carry —
influencing and securing without the card's text, and rerolling without seeing the dice. The plan
for those, and the surfaces they share, is docs/15 section 2.
